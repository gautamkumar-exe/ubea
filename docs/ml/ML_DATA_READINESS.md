# ML Data Readiness

**Assessment date:** 2026-11-03
**Status:** documentation-only review. No model was trained, no production code or schema was changed, and no live event values are included here.

## Readiness summary

The platform has a usable event envelope and an experimental, seven-feature preprocessing path, but it is **not ready for production ML training or inference**. The typed event fields support basic per-user, event-type, timestamp, and source-IP features. They do not currently provide standardized authentication outcomes, reliable event semantics across sources, point-in-time baseline snapshots, or verified event-level labels.

The live API was unavailable and Docker database access was denied during this review. Consequently, this assessment does not claim to know production record volume, null rates, source coverage, duplicate rates, timestamp quality, or label prevalence. Only schema/code and aggregate characteristics of the committed synthetic fixture were inspected. Collect those runtime quality measures from an approved, access-controlled environment before choosing a training cohort.

## What can currently be used for training

Subject to a real-data quality audit and the label policy in [ML_LABELING_POLICY.md](ML_LABELING_POLICY.md):

- `event_time` is suitable for chronological ordering and UTC time derivation when timezone offsets are valid.
- `event_type` is available as a categorical signal, but it has no controlled vocabulary or source-aware normalization contract.
- `user_id` can scope per-user history when present. It is nullable, and identity semantics/coverage require validation.
- `source_ip` can support history/familiarity features after validation and privacy treatment. It is nullable and sensitive.
- `source` can identify provenance, but source-specific semantics and cross-source event equivalence are not defined.
- `entity_id` may be useful as a separate grouping key only after its entity type and relationship to `user_id` are clarified.
- `raw_event` is not generally training-ready. It is an arbitrary nested payload and can include sensitive data, unstable keys, or target leakage. Use only allowlisted, validated, versioned fields after source-by-source review.
- `created_at` is internal ingestion metadata, not behavior time. It may be useful for ingestion-latency diagnostics, but is not exposed in the current list response.

Not currently available as standardized fields: authentication outcome, action/target, device identity/posture, process context, user local time zone, geo/IP reputation, event-source schema version, verified incident outcome, and point-in-time behavioral baseline snapshot. Do not infer these from arbitrary payloads or from the current `is_login` substring feature.

## Current pipeline and principal gaps

1. **Ingest and deduplicate.** The event create schema requires source, external ID, event type, and an aware event time. The database uniqueness constraint is `(source, external_id)`. The API does not trigger active anomaly analysis on insert; current alert generation remains rule-based through the anomaly workflow.
2. **Build experimental features.** Feature history is intended to include only prior events. The SQL history helper scopes by user, but the pure feature helper does not enforce same-user scope on every history row. Any dataset builder must enforce entity isolation and strict event-time causality itself.
3. **Apply current rules.** The anomaly service compares event attributes with a mutable all-history user profile and persists rule evidence. This behavior remains in place; it is not a production ML pipeline.
4. **Use feedback cautiously.** Feedback attaches to alerts. Only alerts with a verified non-null event link can be considered for event-level review candidates, and even then a verdict needs the evidence and reviewer requirements in the labeling policy.

Key readiness gaps are: no approved production training cohort; no measured live data quality; no normalized source/event taxonomy; no explicit missing-IP state in current features; no point-in-time baseline snapshots; no adjudicated event-level label store; and no reproducible snapshot/manifest process.

## Dataset preparation strategy

### 1. Inventory, minimize, and sanitize

- Extract only fields needed for the approved use case. Exclude arbitrary `raw_event` content and direct identifiers by default.
- For approved offline analysis, replace user/entity identifiers with stable keyed pseudonyms so repeated activity remains linkable within the snapshot. Store the key outside the dataset with restricted access and a defined rotation/retention policy.
- Treat source IP as sensitive. If familiarity/count features are required, use an approved stable keyed transformation that preserves equality while avoiding disclosure; document that this removes network-prefix semantics. Do not claim it anonymizes against sequence or auxiliary-data re-identification.
- If time shifting is approved, use a consistent, documented shift per cohort that preserves event order and intended time-of-week behavior. Keep original times and mapping material outside the training export. Do not publish row-level event samples in documentation or source control.
- Redact or exclude comments, credentials, tokens, user content, and payload fields. Apply source-specific allowlists only after a schema and purpose review.
- Restrict snapshots to authorized storage, log access, set retention/deletion dates, and record the approved purpose and owner.

### 2. Resolve duplicates and late events

- Use `(source, external_id)` as the current ingestion identity when both values are valid. Before training extraction, quantify duplicate keys and detect conflicting payloads/timestamps for the same key; retain an auditable resolution outcome.
- Do not deduplicate by `(user_id, event_type, source_ip, event_time)` or whole-row similarity alone: repeated identical activity can be real, and those fields are not a proven event identity.
- The synthetic fixture's exact repeated rows lack source and external ID, so they cannot validate production deduplication behavior.
- Preserve event time separately from ingestion time. Define how late-arriving or corrected events affect snapshot cutoffs and feature histories; never silently reorder by ingestion time as a substitute for event time.

### 3. Handle missing and invalid values explicitly

- Reject or quarantine records that violate required source, external ID, event type, or timezone-aware event-time requirements. Report counts and reasons without placing sensitive values in logs.
- Measure null, blank, malformed, and unmapped rates by source and time period before cohort selection. A field that is optional in the schema is not guaranteed complete enough for a feature.
- Keep a missing `user_id` distinct from an unknown user and from a new user. Exclude it from per-user history features unless a separately defined task supports another grouping.
- Keep missing/invalid source IP separate from valid-but-unseen IP. The current feature helper emits the same zero familiarity/frequency values for these cases; a future feature contract should carry missingness explicitly.
- Do not impute unknown authentication outcome as success or failure, or absent baseline as zero deviation. Use explicit unavailable/unknown handling or exclude the feature/sample according to a versioned rule.
- Validate source-specific `raw_event` fields before use; reject type drift or route it to a documented unmapped value rather than silently coercing.

### 4. Label and class policy

- Default records to unknown/unlabeled. Absence of an alert or feedback is not a normal label.
- Use only evidence-backed normal and confirmed-malicious labels for supervised metrics. Keep suspicious-unconfirmed, inconclusive, conflicts, and unlinked feedback out of binary targets.
- Do not treat every alert, severity, risk score, dismissed status, or rule explanation as a confirmed attack. Preserve detection correctness separately from event maliciousness.
- Publish class counts and their provenance after deduplication and splitting. If positives are rare, retain a temporal holdout and report per-class support; do not rebalance or oversample validation/test data. Any class weighting or training resampling must be fit on training only and documented.
- Account for analyst-review selection bias: investigated alerts are not a representative sample of all events. Label acquisition should include a governed review sampling strategy for non-alerted activity if normal labels are needed.

### 5. Split temporally and prevent leakage

- Define the prediction task and target time before splitting. Use chronological train, validation, and final test windows, with explicit UTC boundaries and any necessary embargo for overlapping windows or delayed labels.
- For future-event detection on known users, keep each user's records chronological so later records never enter earlier features. If the intended claim is generalization to unseen users, hold out entire users as an additional evaluation design; do not mix that claim with the known-user result.
- Construct every history or baseline using only information strictly before the target event. Define a deterministic tie policy for events with equal timestamps. The current all-history `UserProfile.baseline` must not be used as a historical feature without a point-in-time cutoff.
- Fit vocabularies, imputers, scaling, feature selection, and any resampling only on training data. Keep validation for selection and freeze test for final evaluation.
- Resolve duplicates and label conflicts before splitting so linked/copy records cannot cross partitions. Keep post-event analyst outcome, alert status, explanation, and feedback fields out of predictor features.
- Do not rely only on a random split: adjacent events, repeated entities, and shared baselines can make test performance look better than future deployment performance.

### 6. Validate and version every snapshot

Run documented quality gates before a dataset is approved:

- schema and required-field validation, timezone awareness, event-time bounds, and source-specific type checks;
- duplicate-key counts and conflicting duplicate review;
- per-source coverage, null/invalid/unmapped rates, distinct event types, user/entity coverage, and ingestion delay distributions;
- label counts by class, provenance, source, time period, adjudication state, and split, with denominator and exclusions stated;
- checks for temporal leakage, entity overlap consistent with the evaluation claim, and label/feature fields that encode detector outcomes;
- train/validation/test date coverage and minimum class support; drift and collection changes between periods.

Each immutable dataset version should have a manifest containing snapshot ID and content hash; extraction/code version; schema and source-mapping versions; event-time interval and timezone; inclusion/exclusion rules; deduplication and conflict statistics; missingness/quality summary; label taxonomy and provenance version; feature-schema version; split boundaries and entity-splitting policy; package/runtime versions; approver, purpose, access class, retention, and deletion date. Keep row-level exports and pseudonymization keys out of Git; commit only documentation and non-sensitive aggregate reports.

## Readiness gate and next backend milestone

Before model training is considered, an approved real-data audit must establish representative source coverage and data quality, a governed event-level label process must exist, and point-in-time feature generation must be reproducible. Current synthetic metrics do not satisfy these gates.

**Recommended next backend milestone:** implement a read-only, offline dataset snapshot and validation pipeline (no model training or online inference). It should extract an approved time-bounded cohort, apply source allowlists and identifier/IP sanitization, enforce stable-key duplicate accounting, compute point-in-time features, produce temporal split manifests and aggregate quality reports, and fail closed when required quality gates are unmet. In parallel, define a reviewed mechanism to link adjudicated investigation outcomes to event IDs; do not infer labels from alert state.
