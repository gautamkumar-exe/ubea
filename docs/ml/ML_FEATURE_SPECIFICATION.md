# ML Feature Specification

**Status:** data-foundation proposal based on the current schema and experimental feature code. This is documentation only; it does not change APIs, models, preprocessing, or detection behavior.

## Data boundary

The persisted event model is `backend/app/models/security_event.py::SecurityEvent`. The ingestion contract is `backend/app/schemas/security_event.py::SecurityEventCreate`, and the list response is `SecurityEventListItem`. Current fields are:

| Persisted field | Current schema and ingestion behavior | ML-use assessment |
| --- | --- | --- |
| `id` | UUID primary key generated by the database/model. | Record key only; never a behavioral feature. |
| `source` | Required string, max 100 characters; blank values rejected and surrounding whitespace stripped. | Candidate provenance/grouping field after a source vocabulary is defined. Not currently a feature. |
| `external_id` | Nullable in the SQLAlchemy model; required in the create schema, max 255 characters, trimmed and non-blank. Unique with `source` in the database. | Idempotency key only; exclude from features because producer IDs may encode sequence/time or other sensitive identifiers. |
| `event_type` | Required string, max 100 characters; trimmed and non-blank. No controlled enum or source-specific normalization. | Available categorical signal. Current ML code derives a login substring flag and prior-type familiarity, not a validated category taxonomy. |
| `user_id` | Nullable string, max 255 characters. | Current per-user grouping key for baselines and ML history queries. Missing IDs make user-specific features unavailable; do not pool them into one synthetic “unknown user.” |
| `entity_id` | Nullable string, max 255 characters; no entity type or relationship is stored on the event. | Available identifier, but its semantics are unspecified and it is unused by current ML features. Do not treat it as interchangeable with `user_id` without a documented entity model. |
| `source_ip` | Nullable string, max 45 characters; no canonicalization or IP classification in ingestion. | Available raw network indicator. Current ML derives prior familiarity and prior count. It is sensitive and requires a documented normalization/anonymization policy for shared datasets. |
| `event_time` | Required timezone-aware datetime in the create schema; persisted as timezone-aware `DateTime`. | Primary event-time basis for temporal ordering, windows, and UTC time features. Invalid/missing timestamps should be rejected from training snapshots. |
| `raw_event` | Non-null JSON dictionary in storage; request defaults to `{}`. Nested structure and keys are source-defined and not validated by a shared schema. | Not safe as a general feature source. Use only after per-source allowlists, type contracts, redaction, and versioning. |
| `created_at` | Server-generated timezone-aware timestamp in the model. It is not included in `SecurityEventListItem` or the event-create request. | Candidate data-quality/ingestion-latency metadata, not user behavior. Keep separate from event time and do not substitute it when event time is bad. |

The event list response exposes `id`, `source`, `external_id`, `event_type`, `user_id`, `entity_id`, `source_ip`, `event_time`, and `raw_event`, plus pagination metadata. The live event API was not available during this inspection and the Docker socket was inaccessible. Therefore no runtime database rows, live null rates, source distribution, or live duplicate rates were inspected. The only event records inspected here are the committed synthetic fixture; no event values are reproduced in this document.

## Feature status labels

- **Existing ML feature:** already implemented in `backend/app/services/ml_features.py` and listed in `FEATURE_NAMES`.
- **Available source, not implemented:** the necessary structured field exists, but no feature currently derives it.
- **Proposed, source contract required:** the value cannot be reliably derived from current typed event fields. A source-specific schema or reviewed enrichment contract is needed first.
- **Grouping/quality metadata:** useful to scope or validate examples, but not a model input by default.

## Feature definitions

| Feature name | Status / data type | Source field(s) | Transformation | Missing-value handling | Leakage / reliability risks |
| --- | --- | --- | --- | --- | --- |
| `subject_user_key` | Grouping metadata; string, not an input feature | `user_id` | Use as a per-user grouping key. Apply stable pseudonymization for approved exports. | Null means user-scoped features are unavailable. Keep the row for non-user analyses only if the chosen task supports it; never merge all null IDs into one user. | High-cardinality identity memorization and split leakage. The same user in train and test is appropriate only for a per-user future-event task; it does not establish generalization to unseen users. |
| `subject_entity_key` | Available source, not implemented; string grouping metadata | `entity_id` | Preserve separately from `user_id`; resolve entity type/meaning before using it for grouping. | Null remains unknown. Do not copy `user_id` into this field. | It may refer to endpoint, asset, or another subject; there is no event-level entity type. Mixed entity classes can contaminate history. |
| `event_type` | Available source; categorical string | `event_type` | Normalize only with a versioned, source-aware mapping. Preserve a raw-to-canonical mapping for audit. Current code compares exact strings for known-type behavior. | Required in current create schema. Invalid historic rows should be quarantined or explicitly mapped to an “unmapped” category with a missingness indicator; do not silently drop into a normal class. | Source-specific aliases, version changes, or attacker-controlled event names can create spurious novelty. Mapping learned on all time periods leaks future vocabulary. |
| `is_login` | Existing ML feature; numeric 0/1 | `event_type` | Current implementation uses `float("login" in event_type.lower())`. | Event type is required. If historical value is absent/invalid, reject or mark feature unavailable; do not assume non-login. | Substring matching may misclassify custom event names. This is not an authentication outcome. Taxonomy changes can alter meaning. |
| `is_known_event_type` | Existing ML feature; numeric 0/1 | Current `event_type` plus earlier same-user events | Current implementation checks exact event-type presence among prior records. | If no prior history, 0 means “not observed yet”; this is a valid cold-start value, not missing data. Missing user scope makes the feature unavailable. | Future rows or other users in `history` leak information. The pure helper trusts callers to scope history; SQL helper scopes by `user_id`. Same-time events are excluded by strict `< event_time`. |
| `source_ip` | Available source; sensitive network string | `source_ip` | Validate/canonicalize with a standard IP parser before any future categorical/network transformation. Do not perform external reputation or geolocation lookups unless separately approved. | Nullable in schema. Preserve a distinct missing state; current feature helper instead maps absent IP to `is_known_ip=0` and frequency 0, conflating missing with unfamiliar/zero. | IPs can identify people/organizations and may be attacker-controlled. IP rotation, NAT, VPNs, proxies, IPv4/IPv6 formatting, and test/private ranges affect meaning. |
| `is_known_ip` | Existing ML feature; numeric 0/1 | Current `source_ip` plus earlier same-user events | Current implementation checks if the event IP appears in prior history. | If `source_ip` is absent, current code emits 0; this conflates missing with unfamiliar. A production feature contract should add an explicit missing indicator or distinguish unavailable from unseen. No prior occurrences can validly produce 0. | Same-user and strictly earlier history must be enforced. Historical poisoning or repeated untrusted events can make a malicious address appear familiar. |
| `source_ip_frequency` | Existing ML feature; numeric float | Current `source_ip` plus earlier same-user events | Current implementation calculates `log1p(number of earlier occurrences of the same IP)`. | Current code emits 0 when IP is absent or has no prior count; these cases are not distinguished. Future schema should carry missingness separately. | A high count is not inherently benign. Replayed/poisoned history, shared NAT, test duplicates, and unbounded history windows skew the count. |
| `source_ip_family` / network class | Proposed; categorical | `source_ip` | After canonical parsing, optionally derive address family or approved private/public/network-prefix categories. | Missing or invalid IP is an explicit unknown category plus quality flag. | Not implemented. Prefix/address class can reveal infrastructure; must not imply reputation or geographic risk. An anonymization method may destroy network-prefix semantics. |
| `authentication_outcome` | Proposed; categorical | No typed field. Could be in `raw_event` or encoded in `event_type`, but neither has a shared outcome contract. | Add a source-specific, versioned mapping for success, failure, challenge, lockout, etc. Do not infer outcome from `is_login`. | “Not supplied” is distinct from success/failure. Invalid values are rejected or mapped to an explicit unmapped state. | Outcome parsing can leak labels if attack/alert outcome is embedded in the payload. Raw provider keys may change; failure codes may contain sensitive content. |
| `hour_sin`, `hour_cos` | Existing ML features; numeric float pair | `event_time` | Current implementation converts event time to UTC hour plus minute fraction and encodes a 24-hour cycle with sine/cosine. | API requires a timezone; reject invalid/missing times. No fallback to `created_at`. | Only UTC is available as an explicit common frame; no user locale/time zone exists. Incorrect source timezone offsets shift behavior. Historical time must remain causal. |
| `day_of_week` / weekday cycle | Available source, not implemented; categorical or cyclic numeric | `event_time` | Derive in UTC only if the task warrants it; define any local-time semantics separately. | Invalid/missing event time is excluded from temporal training. | Calendar time may proxy geography/work schedules and drift across holidays/shift changes. A shifted/anonymized dataset must document whether weekday patterns are preserved. |
| `user_event_frequency` | Existing ML feature; numeric float | `user_id`, `event_time` | Current implementation counts same-user prior events in the preceding 24 hours and applies `log1p`. | No prior records validly yields 0. Missing `user_id` makes the feature unavailable, not zero. | Duplicates inflate frequency. Must filter strictly before the target and isolate subject. Current pure helper does not itself verify every history row has the target user ID. |
| `event_rate_by_window` | Proposed; numeric float | `user_id`, `event_time` | Consider separate documented counts/rates for fixed windows (for example 1 hour and 24 hours) after choosing the use case. | No prior records is 0; unavailable identity/time is missing/invalid and tracked separately. | Window overlap and future rows can leak. Counts depend on ingestion completeness, deduplication, source coverage, and event-time ties. |
| `event_type_count_deviation` | Proposed; numeric or categorical deviation | `UserProfile.baseline.event_type_counts` or point-in-time same-user history | Compare a target category against a baseline window only after defining denominator and minimum support. Not currently in ML features. | No baseline/not enough support is “unavailable,” not a normal deviation of 0. | Current baseline rebuild uses all stored user events and is not a point-in-time snapshot. Rebuilding after a target event can include that event/future events; using it for retrospective training leaks target/future information. |
| `login_hour_deviation` | Proposed; numeric or boolean | `UserProfile.baseline.login_hour_counts_utc`, `event_type`, `event_time` | Compare login time with a versioned point-in-time baseline. Current rule engine checks whether an hour was observed; ML helper uses `hour_sin/cos`, not this saved baseline. | No baseline or no login-hour observations is unavailable; not “normal.” | Saved baseline may include target/future events and has no training window/version. UTC hour may not reflect a user's local routine. |
| `source_ip_baseline_deviation` | Proposed; numeric/categorical | `UserProfile.baseline.source_ip_counts`, `source_ip` | Could compare against point-in-time known IP count or proportion; choose and version exact formula. Current rule engine checks unfamiliar IP; current ML helper uses past history directly. | Missing IP or no baseline is distinct from unseen IP. | Baseline counts can become poisoned by repeated events. Existing baseline is an all-history summary, can leak future data in retrospective evaluation, and lacks a staleness policy. |
| `active_day_baseline_deviation` | Proposed; numeric | `UserProfile.baseline.active_days`, event time | Derive daily activity deviations only after defining time zone, lookback window, and denominator. | No baseline/window support is unavailable. | Current `active_days` is a lifetime count from the baseline rebuild, not a per-day or rolling rate. Retrospective builds leak later days. |
| `source` | Available source, not implemented; categorical | `source` | Normalize to a controlled producer/source class if provenance is useful. Keep original source for audit under access controls. | Required and blank rejected at ingestion. Historic blanks should be quarantined or explicit unknown. | May encode environment/customer identity or ingestion route. High-cardinality integration names can cause source memorization. |
| `ingestion_delay` | Available model metadata, not an existing feature; numeric duration | `created_at - event_time` | Derive as a data-quality/latency measure, not user behavior. `created_at` is server-set but omitted from list responses. | If either timestamp is invalid, mark unavailable and flag quality. | Late-arriving events and timezone errors can make delay negative or misleading. Do not use `created_at` to replace event chronology. |
| `external_id`, event `id` | Grouping/idempotency metadata; exclude as feature | `external_id`, `id` | Use only for record linkage/dedup/audit. Existing uniqueness is `(source, external_id)`. | Missing historical external IDs require a quality flag; do not invent them from behavior fields. | Identifier sequences often encode source/time and can leak split membership, collection paths, or PII. |
| Arbitrary payload fields | Proposed only after contract; heterogeneous types | `raw_event` JSON | Per-source allowlist, schema version, type validation, normalization, and redaction must precede transformation. | Define per-key missing/unmapped behavior; do not coerce arbitrary objects to numbers or silently substitute zero. | Payload can contain secrets, credentials, user content, or labels; schema drift and target leakage are uncontrolled today. |

## Current seven-feature vector

`backend/app/services/ml_anomaly.py::FEATURE_NAMES` defines the exact vector order:

1. `hour_sin`
2. `hour_cos`
3. `is_login`
4. `is_known_ip`
5. `is_known_event_type`
6. `user_event_frequency`
7. `source_ip_frequency`

Do not change ordering or semantics for any future persisted model without a new feature-schema version. The `scenario` field in `backend/scripts/reports/synthetic_events.csv` is a synthetic experiment label; it is not an event feature and does not exist in the production `SecurityEvent` schema.

## Point-in-time baseline contract

The current `UserProfile.baseline` JSON can contain `event_count`, `event_type_counts`, `login_hour_counts_utc`, `source_ip_counts`, `active_days`, `first_seen`, and `last_seen`. `backend/app/services/baseline.py::build_user_baseline` rebuilds it from all stored events for a user and overwrites the previous JSON. It records no snapshot ID, time window, or feature version. `backend/app/services/anomaly.py` uses this profile for the active rule-based evaluation.

For ML training or retrospective evaluation, do not directly treat that mutable all-history JSON as the target event's baseline. Build features from events strictly before the target (with an explicit tie policy), or persist a point-in-time baseline snapshot and its cutoff. Keep current rule behavior unchanged until a separately reviewed implementation decision.
